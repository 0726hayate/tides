# Tides v1.1 Polish Spec

**Date:** 2026-05-20
**Status:** Approved for plan
**Working dir:** `/home/hayate0726/cycles`
**Tech stack:** Android, Kotlin 2.0, Compose, Hilt, Room/SQLCipher

## Goal

Close six v1.0 polish items uncovered after the v1.0.0 / v1.0.1 install: palette drift from the source mockup, missing PIN-shuffle setting, missing onboarding interruption persistence, incomplete onboarding flow (no flow + symptoms capture), no prediction preview after onboarding, and missing interpretation copy on the existing Stats screen.

## Architecture

Six sequential commits, each independently testable, ordered low-risk to high-risk. Touches the onboarding subsystem (commits 4–6), the appearance/lock subsystem (commits 1–2), and the existing Stats screen (commit 3). No new entity tables, no Room migrations, no networking. All work additive to existing files where possible.

## Commit Plan

1. **#3 palette recalibration** — recalibrate `TidesColors.kt` swatches to Direction 3 mockup.
2. **#9 PIN shuffle** — opt-in Settings toggle, new `ShuffledPinKeypad`, wired only into `LockScreen`.
3. **Stats educational copy** — `StatsInfoSheet` component + per-chart "How to read this" bottom sheets.
4. **#6 onboarding draft persistence** — `OnboardingDraftStore` + Welcome resume/restart prompt.
5. **#4 flow + symptoms screen** — new `FlowSymptomsScreen` after `LastPeriodScreen`.
6. **#5 prediction preview** — new `PredictionPreviewScreen` between flow-symptoms and complete.

## In / Out of Scope

**In scope:**
- Additive props on `CalendarMonth` (no structural rewrite).
- Targeted change to `PhaseCalculator` to handle single-cycle input via `assumeCycleLength`.
- Reuse of existing `SymptomEntryEntity` and `CycleEntryEntity`.

**Out of scope:**
- New entity tables / Room migrations.
- Algorithm changes to `PhaseCalculator` beyond single-cycle support.
- Any networking, telemetry, or analytics-that-phone-home (banned by mission).
- Health Connect / Samsung Health import — deferred to v1.2 with its own brainstorm.
- Localization. English only.

## Commit 2 — #9 PIN Shuffle

**Setting:** `AppearanceRepository` gains `shufflePinKeypad: StateFlow<Boolean>` (key `"shuffle_pin_keypad"`, default `false`). Same `SharedPreferences` file as the existing `useDynamicColor` and `themeMode`. No PIN material involved.

**Settings UI:** new row in `AppearanceScreen` under the existing Theme + dynamic-color rows: `"Shuffle PIN keypad"` switch + helper text:
> "Randomizes the keypad layout on the lock screen to defeat shoulder surfing and screen smudging. PIN setup is not shuffled."

**Component:** new `ShuffledPinKeypad.kt` in `ui/lock/`. Same composable API as `PinKeypad` (`onDigit: (Int) -> Unit`, `onBackspace: () -> Unit`, `modifier: Modifier`).

Internals:
- `remember(lockShowKey) { (1..9).shuffled() }` produces the digit order for slots 1–9.
- Bottom row: blank, `0`, `⌫` — fixed positions. `0` stays fixed (small information leak accepted), `⌫` stays fixed (moving it is hostile to motor-impaired users).
- `lockShowKey` is a unit `Any()` created in a `LaunchedEffect` on `LockScreen` entry. Reshuffles per show, not per keystroke or per attempt.

**Wiring:** `LockHost.kt` collects `shufflePinKeypad` from `AppearanceRepository` (already accessible via Hilt entry point pattern) and selects between `PinKeypad` and `ShuffledPinKeypad`. `PinSetupScreen` remains on `PinKeypad`.

**Accessibility:** each digit button preserves `contentDescription = "<digit>"`. Screen-reader announcement is value-based, not position-based — TalkBack users are unaffected by the visual shuffle.

**Tests:**
- Unit on `ShuffledPinKeypad` shuffle logic: digits 0–9 all present exactly once; `0` and `⌫` in fixed slots.
- Compose on `LockScreen`: with shuffle on, a deterministic seed produces a known non-canonical order.
- Instrumented: toggle shuffle in Settings → return to lock → keypad layout differs from canonical.

## Commit 3 — Stats Educational Copy

**New file:** `StatsInfoSheet.kt` in `ui/stats/`. Reusable `ModalBottomSheet` with `title: String`, `body: AnnotatedString`, optional `sources: List<Source>` where `Source = data class(label: String, citation: String)`.

**Trigger:** small `Icon(Icons.Outlined.Info)` button in the top-right of each chart card. Existing chart components (`CycleLengthChart`, `PeriodLengthTrend`, `SymptomHeatmap`, `SymptomFrequencyList`, `InsightCard`) gain an `onInfoClick: (() -> Unit)? = null` optional parameter. `StatsScreen` wires each one to open the sheet with chart-specific copy.

**Content per chart:**

| Chart | Copy (≤ 3 sentences) | Sources |
|---|---|---|
| Cycle length | What a cycle is (period start → next period start). Typical adult range is **21–35 days** per FSRH. Variation of a few days is normal; consistent shifts of 7+ days may be worth a check-in. | FSRH 2023; ACOG FAQ |
| Period length | What we measure (consecutive bleeding days). Typical range **2–7 days**. Longer than 8 days or heavier-than-usual may warrant a clinical check. | NHS; ACOG |
| Symptom heatmap | Darker cells = more days that symptom was logged in that cycle phase. Patterns repeating across cycles are more meaningful than single occurrences. | — |
| Symptom frequency | Total days each symptom appeared in the visible range. Useful for spotting clusters or new patterns over time. | — |
| Insight cards | Observations from your data, not medical advice. Generated locally; nothing leaves your device. | — |

**Source-citation format:** plain text at the bottom of the sheet — e.g. *"Sources: FSRH 2023 — Normal Menstruation; ACOG FAQ — Your Menstrual Cycle."* No URLs (no `INTERNET` permission). Users search the cited titles themselves.

**Copy storage:** `StatsInfoCopy.kt` — `object StatsInfoCopy { val cycleLength: SheetCopy = ...; ... }`. Keeps strings out of composables.

**Privacy footer:** every sheet ends with *"All charts are generated on your device. Nothing is uploaded."*

**Tests:**
- Unit: every chart key has non-empty title and body in `StatsInfoCopy`.
- Compose: tapping info icon on each chart opens a sheet with the expected title.
- Existing Stats instrumented tests remain valid (additive change).

**Excluded:** diagnostic claims ("PCOS pattern detected"), per-user threshold customization (v2 notifications), translation.

## Commit 4 — #6 Onboarding Draft Persistence

**New file:** `OnboardingDraftStore.kt` in `ui/onboarding/`. Plaintext `SharedPreferences` (`onboarding_draft.xml`, `MODE_PRIVATE`). Mirrors the `AppearanceRepository` pattern.

**Persisted shape (`SafeDraft`):**
```
goals: Set<Goal>                   // enum CSV
birthControl: BirthControlMethod   // enum name
biometricEnabled: Boolean
lastPeriodStart: LocalDate?        // ISO date or null
flow: FlowIntensity?               // field defined here, populated by Commit 5
symptoms: Set<Symptom>             // field defined here, populated by Commit 5
currentStep: OnboardingStep        // GOALS|THREAT|BC|PIN|BIOMETRIC|LAST_PERIOD|FLOW_SYMPTOMS|PREDICTION
createdAt: Long                    // epoch ms, for expiry
```

`OnboardingStep` is a new enum introduced in this commit. The `FLOW_SYMPTOMS` and `PREDICTION` values are valid step targets only after Commits 5 and 6 land; until then, the resume nav routes them to `COMPLETE` (no-op fallback).

**Never persisted:**
- `pinChars` — explicitly stripped on every write. Re-typed on resume.
- `threatPreset` — excluded for threat-model reasons (an attacker with adb/root could see the user was considering `DURESS`, which itself is a disclosure in abusive-partner scenarios). Re-prompted on resume (~10 second redo).

**Expiry:** drafts older than **7 days** are auto-deleted on next launch.

**Welcome screen change:** on composition, check `draftStore.exists()`. If true, render a `Surface` card above the welcome content:
> **Resume your setup?**
> You started setting up Tides earlier. We saved the goals you picked but never your PIN.
> [Resume] [Start over]

- **Resume** → `onboardingViewModel.resumeFromDraft()` → navigate to `currentStep`.
- **Start over** → `AlertDialog` *"Discard your earlier setup and start fresh?"* → on confirm: `draftStore.clear()`, normal welcome flow.

**OnboardingViewModel changes:**
- Inject `OnboardingDraftStore`.
- After every non-PIN setter, debounce-write to the store (200ms via a single coroutine `Job` cancelled on each new write).
- PIN setter (`setPin`) updates in-memory draft only — never writes to the store.
- New `fun resumeFromDraft()`: loads store → populates `DraftState` → emits `currentStep` for nav routing.
- New `fun startFresh()`: clears store, resets `DraftState`.
- `complete()`: clears store after `key.zero()`.

**Navigation:** `MainNavGraph` reads `currentStep` from the draft on resume and starts the onboarding subgraph at that route.

**Tests:**
- Unit on `OnboardingDraftStore`: round-trip save → load returns same `SafeDraft`; `pinChars` round-trips as null; drafts older than 7 days fail `exists()`; `threatPreset` field absent from persisted data.
- Compose on Welcome: with `draftStore.exists() = true`, resume card renders; "Start over" shows confirm dialog.
- Integration: process-recreation test mid-onboarding → draft persists → resume routes to the correct step.

**Excluded:** draft encryption (no PIN yet to derive a key; 7-day-max plaintext of non-secret choices is acceptable), cross-device sync, draft preview on the resume card beyond the one-liner.

## Commit 5 — #4 Flow + Symptoms Onboarding Screen

**New file:** `FlowSymptomsScreen.kt` in `ui/onboarding/`. Shown only when the user picked a date on `LastPeriodScreen`; skipped entirely on "Skip date".

**Layout:**
```
"How was that period?"
"Helps your first predictions and chart."

— Flow —
[Light]  [Medium]  [Heavy]       (SegmentedButtonRow, single-select, required)

— Anything else? (optional) —
[Cramps]  [Headache]  [Bloating]
[Tired]   [Irritable] [Sad]
[Cravings] [Acne]     [Breast tenderness]
                                  (FilterChip grid, multi-select)

[Skip the rest]  [Save]
```

**Curated symptom subset (9 chips):**
- Pain: `CRAMPS`, `HEADACHE`, `BREAST_TENDERNESS`
- Body: `BLOATING`, `ACNE`
- Mood: `IRRITABLE`, `SAD`
- Energy: `TIRED`
- Digestive: `CRAVINGS`

Selected to keep the screen single-viewport on a 360dp width and cover highest-base-rate symptoms. Full logging available later via the Log sheet.

**`DraftState` additions:**
```kotlin
data class DraftState(
    ...
    val flow: FlowIntensity? = null,
    val symptoms: Set<Symptom> = emptySet(),
)

fun setFlow(f: FlowIntensity)
fun setSymptoms(s: Set<Symptom>)
```

`equals`/`hashCode` already overridden in `DraftState`; both new fields use value equality (enum + Set) — no additional code needed.

**`complete()` changes:**
1. Replace hardcoded `FlowIntensity.LIGHT` with `draft.flow ?: FlowIntensity.LIGHT` (defensive default; the screen enforces flow selection).
2. After the `cycleEntryDao.upsert(...)` call, write a `SymptomEntryEntity` for each selected symptom, all dated to the period start date.

**Navigation graph update:**
```
... → LastPeriod
  → (date picked?) → FlowSymptoms → Prediction → Complete
  → (skip)         → Complete
```

**Skip path:** "Skip the rest" on `FlowSymptomsScreen` skips only symptoms — flow is still required. To skip both, the user uses "Skip date" on the previous `LastPeriodScreen`.

**Tests:**
- Unit on `OnboardingViewModel`: setting flow + symptoms, calling `complete()`, verifying the DB has one `CycleEntry` with the chosen flow + N `SymptomEntries` with `date == lastPeriodStart`.
- Compose: chip toggle works; "Save" disabled until flow picked; "Skip the rest" calls `complete()` with empty `symptoms`.
- Visual: chip grid wraps without horizontal scroll on 360dp width.

**Excluded:** symptom intensity (mild/moderate/severe), free-text `OTHER`, period-range symptom tagging beyond the start day.

## Commit 6 — #5 Prediction Preview

**New file:** `PredictionPreviewScreen.kt` in `ui/onboarding/`.

**Layout:**
```
"Here's your first prediction"
"Based on a 28-day default. It'll get sharper as you log more."

[CalendarMonth — positioned to month of lastPeriodStart]
  - Entered period (lastPeriod..lastPeriod+4): existing period-day style.
  - Predicted next period (lastPeriod+28..lastPeriod+32): same shape, 50% opacity.
  - Fertile window (lastPeriod+12..lastPeriod+16): existing ovulation overlay, only when PhaseCalculator returns non-null.

"Next period: ~ <Month Day>"
"Fertile window: ~ <Month Day> — <Month Day>"        (only when shown)

[Edit]                              [Looks good]
```

**Data flow:**

1. New `PredictionPreviewViewModel`:
   - Reads `OnboardingViewModel.draft` flow.
   - Constructs a synthetic active cycle: `Cycle(start = lastPeriodStart, end = null, isActive = true, length = null, periodLength = null)`.
   - Calls `PhaseCalculator.compute(cycles = listOf(synthetic), today = lastPeriodStart, birthControl, goals, assumeCycleLength = 28)` to get the fertile window.
   - Computes `predictedPeriodDays = (lastPeriodStart + 28 days .. lastPeriodStart + 32 days)` directly (no PhaseCalculator dependency).
   - Computes `enteredPeriodDays = (lastPeriodStart .. lastPeriodStart + 4 days)`.

2. `CalendarMonth` additive prop (only one new prop needed):
```kotlin
@Composable
fun CalendarMonth(
    state: CalendarMonthState,
    view: CalendarView,
    onDayClick: (LocalDate) -> Unit,
    modifier: Modifier = Modifier,
    predictedPeriodDays: Set<LocalDate> = emptySet(),
)
```

Day cell logic adds: if `date in predictedPeriodDays`, render period background at 50% alpha. Existing CVD-safe shape glyph still applies.

The fertile window is plumbed via the existing `ovulationWindow` field on `CalendarMonthState` (already used by `CalendarViewModel.UiState`). `PredictionPreviewViewModel` constructs a `CalendarMonthState` with `ovulationWindow` set to the predicted range — no new prop needed for the fertile overlay.

**`PhaseCalculator` change (targeted):**

Add `assumeCycleLength: Int? = null` parameter to `compute()`. When `completedLengths.isEmpty()` and `assumeCycleLength != null`, use `assumeCycleLength` as the median. Trust window (21–35) still applies — `assumeCycleLength = 28` works; `assumeCycleLength = 40` still returns null. Confidence forced to `LOW` in this branch.

All other algorithm logic unchanged. Existing tests unaffected.

**Goal-gated suppression preserved:** if goals don't intersect `Goal.OVULATION_RELEVANT` or `birthControl.isHormonal`, `PhaseCalculator.compute()` returns null → fertile-window overlay + caption hidden. Predicted next period still shows (it's not ovulation data).

**Hormonal BC note:** when `birthControl.isHormonal`, append a one-liner caption: *"Hormonal birth control can change your cycle. Predictions adjust as you log."* Empirical, no special algorithm.

**Buttons:**
- **Edit** → navigates back to `LastPeriodScreen` (most edits are date corrections). Draft state preserved by `OnboardingDraftStore` from Commit 4.
- **Looks good** → triggers `OnboardingViewModel.complete()`; nav falls through to `OnboardingComplete`.

**Edge cases:**
- `lastPeriodStart` near month-end → predicted period falls into next month. Decision: render only the month of `lastPeriodStart` with the predicted days clipped; caption communicates the exact next date.
- User skipped `LastPeriodScreen` → `PredictionPreviewScreen` never shown.
- `goals = {TRACK_PERIOD}` only → fertile window hidden, predicted next period shown.
- `birthControl = HORMONAL_IUD` → fertile window hidden + hormonal-BC caption shown.

**Tests:**
- Unit on `PhaseCalculator`: `assumeCycleLength = 28` with empty `completedLengths` returns ovulation window centered on day 14 ±2; `assumeCycleLength = 40` returns null. All existing tests still pass.
- Unit on `PredictionPreviewViewModel`: predicted period days = days 28–32 from start; fertile window = days 12–16 when goals/BC allow.
- Compose on `PredictionPreviewScreen`: hormonal BC → fertile-window caption hidden, hormonal-BC caption shown; `AVOID_PREGNANCY` + non-hormonal BC → fertile-window caption shown.
- Visual: predicted period cells visually distinct from entered period cells (reduced opacity).

**Excluded:** multi-month view, reminder-scheduling CTA, drag-to-edit on the calendar, hormonal-BC-specific prediction modeling.

## Testing Strategy Summary

- Each commit's tests run independently; commit ordering chosen so later commits don't break earlier tests.
- Existing real-world validation suite (21 personas, 184 tests) gates correctness for `PhaseCalculator` changes in Commit 6.
- Visual verification: regenerate screenshots in Commit 1; manual emulator walkthroughs at end of each commit.
- No new instrumented test files for Commits 1 and 3; all others add at least one Compose or integration test.

## Risks and Open Questions

- **Risk:** Direction 3 mockup dark-theme drift not addressed. Mitigation: the existing dark theme is consistent with the warm-privacy intent; revisit when a dark mockup exists.
- **Risk:** Plaintext draft persistence is a privacy footprint visible to forensic tooling. Mitigation: 7-day expiry, `threatPreset` excluded, PIN never persisted. Documented in spec for future revisit if threat model tightens.
- **Open:** symptom curation list (9 chips) was a designer's pick; if the v1.1 install confirms the picks are wrong, easy to swap without code refactor (`StatsInfoCopy`-style constants).
