# v1.2 — Data Import From Other Apps

> Design spec. Implementation plan to follow.

## Goal

Let users migrate period history into Tides from three other apps without leaving the device or talking to any network:

1. **Samsung Health** — HTML report from "Share data"
2. **Clue** — CSV from "Download my data"
3. **drip** — JSON export from "Backup → Export"

Entry points: the Onboarding Welcome screen (fresh migration) and Settings → Data (post-onboarding backfill).

## Non-Goals

- Apple Health, Flo, Period Tracker, or other source apps (defer until users ask)
- Samsung Health PDF parsing (HTML covers the same data with far less code)
- Cloud-based import paths (Samsung Health SDK, OAuth flows) — violates the no-INTERNET stance
- Two-way sync — this is one-shot import, not ongoing replication
- Importing fields Tides does not model today (BBT, cervical mucus, sex log, mood). They are surfaced as "couldn't import" and dropped.

## Decisions (locked)

| Decision | Choice |
|---|---|
| Sources | Samsung Health (HTML), Clue (CSV), drip (JSON) |
| Data scope | `CycleEntryEntity` (date, flow, pain, notes) + `SymptomEntryEntity` rows |
| Entry points | Onboarding Welcome AND Settings → Data |
| Conflict policy | Skip imported when date already has a Tides entry. Idempotent re-import. |
| Preview | Required before commit |
| Snapshot | Auto-snapshot DB before each import. One slot, overwritten on next import. |
| Unmapped fields | Report counts in preview, drop on commit. Raw values never surfaced. |
| Rollback | "Roll back last import" in Settings → Data, visible only when snapshot exists. Confirm dialog, no PIN gate. |
| Samsung format | HTML only via JSoup. PDF rejected with helpful error. |

## Architecture

```
data/import/
  ImportSource.kt              # interface
  ImportedEntry.kt             # parsed-row shared model
  ParseResult.kt               # entries + unmapped + warnings
  ImportFormatDetector.kt      # sniff bytes → pick ImportSource
  SamsungHealthHtmlImporter.kt # JSoup parser
  ClueImporter.kt              # CSV parser
  DripImporter.kt              # JSON parser
  ImportPipeline.kt            # detect → parse → diff → preview → write
  PreImportSnapshot.kt         # copy encrypted DB before write

ui/import/
  ImportViewModel.kt
  ImportScreen.kt              # file picker entry
  ImportPreviewScreen.kt       # preview + confirm
  ImportResultScreen.kt        # post-import summary
```

**Pipeline phases:**

1. `pick` — Storage Access Framework opens a document picker; user selects a file (Tides does not request `READ_EXTERNAL_STORAGE`).
2. `detect` — `ImportFormatDetector` reads the first ~4 KB, identifies one of `{SAMSUNG_HTML, CLUE_CSV, DRIP_JSON, PDF, UNKNOWN}`. Encrypted drip backups also begin with JSON and are classified as `DRIP_JSON` at this stage; the encryption check happens inside `DripImporter.parse`, which throws a typed `EncryptedBackup` exception so the UI can surface the specific "drip backup is encrypted" error.
3. `parse` — the matched `ImportSource` reads the full stream on `Dispatchers.IO`, returns `ParseResult(entries, unmapped, warnings)`.
4. `diff` — `ImportPipeline.computePreview(parseResult)` reads `cycleEntryDao.allDates()` once and produces a `PreviewState`. No DB writes yet.
5. `confirm` — user taps Import on `ImportPreviewScreen`.
6. `snapshot` — `PreImportSnapshot.take()` copies the encrypted SQLCipher DB file to `context.filesDir/tides-pre-import.db`. Abort if disk has <25 MB free.
7. `commit` — one Room transaction. For each `ImportedEntry`:
   - If the date already exists in `cycleEntryDao.allDates()` OR appears in `symptomEntryDao.allDates()`, **the whole entry is skipped** (CycleEntry AND symptoms). This makes re-import fully idempotent — re-running the same file produces zero changes.
   - Otherwise: if the entry has `flow != null` or `painSeverity != null` or `notes != null`, insert a `CycleEntryEntity` (with `flowIntensity = flow ?: FlowIntensity.NONE`). Insert one `SymptomEntryEntity` per symptom in the entry.
   - All-or-nothing: any insert failure rolls back the entire transaction.
8. `result` — navigate to `ImportResultScreen` with `(addedDates, skippedDates)`, where `addedDates` is the count of unique dates for which we wrote at least one row.

Cancel at any phase before `commit` is a no-op (no DB writes have happened). Cancel during or after `commit` is impossible — Room's transaction commits atomically. Recovery from regret uses the snapshot via Settings → Roll back last import.

## Data Models

```kotlin
// data/import/ImportedEntry.kt
data class ImportedEntry(
    val date: LocalDate,
    val flow: FlowIntensity?,
    val painSeverity: Int?,
    val symptoms: List<Symptom>,
    val notes: String?,
)

// data/import/ParseResult.kt
data class ParseResult(
    val entries: List<ImportedEntry>,
    val unmapped: List<UnmappedField>,
    val warnings: List<String>,
)

data class UnmappedField(
    val sourceName: String,
    val sampleCount: Int,
)

// data/import/ImportSource.kt
interface ImportSource {
    val displayName: String
    suspend fun parse(stream: InputStream): ParseResult
}

// data/import/ImportPipeline.kt — PreviewState
data class PreviewState(
    val sourceName: String,
    val totalEntries: Int,
    val newDates: Int,
    val conflictingDates: Int,
    val unmapped: List<UnmappedField>,
    val warnings: List<String>,
)
```

### Per-parser translation tables

Each parser owns a private `Map<String, Symptom>`. Examples (final tables verified against fixtures during implementation):

**ClueImporter:**
```kotlin
// Only names that map to a Tides Symptom appear here. Names absent from the
// map are reported as UnmappedField (e.g. unknown wellness columns).
// Column names use Clue's documented snake_case export schema.
private val SYMPTOM_MAP: Map<String, Symptom> = mapOf(
    "cramps" to Symptom.CRAMPS,
    "breast_tenderness" to Symptom.BREAST_TENDERNESS,
    "headache" to Symptom.HEADACHE,
    "bloating" to Symptom.BLOATING,
    "acne" to Symptom.ACNE,
    "fatigue" to Symptom.TIRED,
    "cravings" to Symptom.CRAVINGS,
    "sad" to Symptom.SAD,
    "sensitive" to Symptom.SENSITIVE,
    "happy" to Symptom.HAPPY,
    // Complete list assembled during implementation from Clue's documented
    // export schema and the fixture file. Additional mappings may be added
    // as new column names are observed in real-world exports.
)
```

**SamsungHealthHtmlImporter:** Samsung's "Share data" HTML report contains only period-date ranges (e.g. "Apr 8–10", "Feb 20–Apr 7") in a "Cycle history" table — no per-day flow column and no symptom table. The parser expands each range into one `ImportedEntry` per day with `flow = FlowIntensity.LIGHT` as a baseline marker that a period was logged. Symptom mapping is intentionally not implemented for this source.

**DripImporter:** maps drip's `symptoms` JSON keys (drip is FOSS, full enum lives in their schema).

### Intensity mapping

- **Clue flow** (`light`/`medium`/`heavy`/`spotting`) → `FlowIntensity.{LIGHT, MEDIUM, HEAVY, SPOTTING}`. Tides' `FlowIntensity` already has `SPOTTING` (intCode=1) so the mapping is 1:1.
- **Samsung flow** — the "Share data" HTML report does not include per-day flow intensity. Each day in a period range gets `FlowIntensity.LIGHT` as a baseline ("a period was logged"). If a future Samsung Health version exposes per-day flow, this mapping can be extended.
- **drip symptom intensity** (0/1/2/3) → Tides `severity` (`0→0, 1→0, 2→1, 3→2`).
- **Pain (NRS 0-10)**: source values >10 are clamped to 10 and counted as a warning; <0 rejected as a warning.

Confirm → `PreImportSnapshot.restore()` swaps the snapshot file back into place, then `AppViewModel` re-opens the DB. On successful restore the snapshot file is deleted (single-slot semantics — no chains of rollbacks). On restore failure the snapshot is preserved so the user can retry.

## Error Handling

### File-level errors (Snackbar on ImportScreen, no DB writes)

| Scenario | Behavior |
|---|---|
| File >50 MB | "File is unusually large. Make sure it's a period export, not a full data dump." |
| Unrecognized format | "Couldn't recognize this file. Make sure it's from Samsung Health, Clue, or drip." |
| PDF picked | "PDF isn't supported. Re-export and choose HTML, CSV, or JSON." |
| Encrypted drip backup | "This file is encrypted. Tides can only read unencrypted drip exports — choose 'Export → JSON' instead of 'Backup'." |
| Corrupt/truncated | "File appears damaged. Try re-exporting from the source app." |
| Read I/O error | "Couldn't read the file. Try a different location." |

### Parse-level issues (warnings in preview, parse continues)

- Date in unrecognized format → row skipped, counted in `warnings` ("4 rows had unreadable dates").
- Date in the future or before 1900 → row skipped, counted.
- Symptom name not in translation table → counted as an `UnmappedField`.
- Flow value not mappable → row imported without flow, counted.
- Pain value out of 0-10 → clamped to range, counted.

### Commit-level failures

- Snapshot copy fails (disk full) → abort import: "Not enough space to save a backup before importing. Free up some space and try again."
- Room transaction fails mid-write → Room rolls back automatically. Snapshot untouched. "Import failed. No changes were made."
- App killed during import → next launch sees either a complete commit or rolled-back state (Room's WAL guarantees). Snapshot remains for manual rollback.

### Resource limits

- Parsing on `Dispatchers.IO`. Cancellation honored.
- Full `List<ImportedEntry>` in memory during preview. ~100 bytes/entry × 3,650 entries (10 years daily) ≈ 360 KB. Acceptable.
- One Room transaction wraps all inserts (rollback correctness).

## Privacy

- Imported source file is read, never copied. Tides reads from the SAF URI; the file stays at the user's chosen location.
- `unmapped` reports counts only ("BBT: 45 readings"), never raw values.
- Snapshot file is the Tides DB, not the import file. Lives in `context.filesDir/tides-pre-import.db`, protected by SQLCipher with the same key as the live DB.
- `ImportResultScreen` nudges the user to delete the export file. Tides does not auto-delete files outside its sandbox.

### Fixture sourcing

- **Samsung Health HTML**: user-provided real export, scrubbed (dates shifted +90 days, free text redacted to "REDACTED"). Committed under `app/src/test/resources/import-fixtures/samsung_health_period.html`.
- **drip JSON**: pulled from drip-app's GitHub test fixtures or built against their open schema. Committed as `drip_export.json`.
- **Clue CSV**: synthetic, built against Clue's published "How do I download my data?" support doc. Committed as `clue_export.csv`. Known risk: real Clue exports may drift from docs; mitigated by inviting early users to report parse failures.

### Known follow-up risks

- Clue parser may need format adjustments after first real user runs it. Triage path: ship in v1.2, fix in v1.2.1 if real-world failures land.
- Samsung Health's HTML report markup may change in a future Samsung Health release. JSoup selectors should be loose (text-content based rather than DOM-position based) to reduce blast radius.

## Dependencies (build.gradle.kts)

- `implementation("org.jsoup:jsoup:1.17.2")` — Samsung HTML parsing. ~700 KB.
- No new dependencies for Clue (use standard CSV parsing) or drip (use `kotlinx.serialization.json`, already present for Tides backup format).

## Implementation Order (informational — final order in plan)

A six-task TDD breakdown maps roughly to:

1. Shared models + `ImportSource` interface + `ImportFormatDetector` (no parsers yet — pure scaffolding + detector tests).
2. `DripImporter` (cleanest schema, used as the reference parser).
3. `ClueImporter` (CSV; synthetic fixture).
4. `SamsungHealthHtmlImporter` (HTML; real fixture; JSoup dependency added here).
5. `ImportPipeline` + `PreImportSnapshot` + Room write path + result models.
6. UI: `ImportScreen`, `ImportPreviewScreen`, `ImportResultScreen`, Onboarding wiring, Settings wiring, rollback path.
